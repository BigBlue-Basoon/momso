개발 Linux VM은 48GB 중 약 9.5GB 사용, 약 38GB 여유였다. 제품 설치 폴더가 없어 다른 항목을 그 VM에서 측정하지 못했다.

## 구현한 보호

- 업데이트 성공과 서버·입구 확인, 유지보수 해제 뒤에만 관리 표시가 있는 옛 판을 정리한다. 현재 판과 직전 판은 남긴다. 자료 사본은 기본 최신 2개와 이번 복구용 사본을 남긴다. `MOMSO_UPDATE_SNAPSHOT_KEEP`로 최근 사본 수를 조정할 수 있으며 잘못된 값이면 삭제하지 않는다. 미완료 업데이트에서는 정리하지 않는다.
- 업데이트 전에 빈 공간이 1.5GiB 미만이면 완료된 갱신 기록이 있는 경우 안전한 옛 판·사본을 먼저 정리하고, 그래도 부족하면 파일을 받기 전에 `disk_low`로 거절한다. 첨부 시작과 조각 업로드는 보낼 크기와 여유 공간을 확인하고, 브라우저를 새로 열기 전에도 확인한다.
- 인증된 HTTP의 새 쓰기 요청도 같은 기준으로 막는다. 중단·승인 응답·복구·삭제 등 마무리나 공간 확보에 필요한 요청은 계속 허용한다. 일반 쓰기는 진행 중인 큰 쓰기의 예약 크기도 여유에 더한다. 예약에 참여하지 않는 외부 프로그램의 쓰기는 막을 수 없다.
- AI의 문서 생성과 자료 모으기 쓰기 도구도 시작 전에 같은 기준을 확인한다.
- 브라우저를 새로 열기 전이나 새 HTTP 쓰기를 공간 부족으로 거절하기 전, 30일 이상 된 각 방의 `Cache`, `Code Cache`, `GPUCache`만 정리하고 공간을 다시 확인한다. 방을 열거나 닫은 시각을 방별 잠금 파일에 남겨 30일이 지나야 하며, 실행 중 잠금과 Chromium의 실행 중 표시가 있는 방은 건너뛴다. 기록이 없던 기존 방은 최초 확인부터 30일을 기다린다. 고정한 디렉터리에서만 지운다. 쿠키·로그인·로컬 저장소는 정리 경로에 넣지 않는다. 확인할 수 없는 폴더도 건너뛴다.
- 업데이트 작업자가 설치·시작될 때 전용 journald 설정을 만든다. 영구 저널은 200MiB, 휘발성 저널은 64MiB 상한을 설정한다. 20GB 디스크의 약 1%를 영구 로그에 배정한 운영상 기본값이며, 다른 이름의 관리 설정을 지우지 않고 같은 파일에 기존 다른 내용이 있으면 보존하고 충돌을 기록한다. [systemd 공식 설명](https://www.freedesktop.org/software/systemd/man/250/journald.conf.html)에 따르면 영구·휘발성 저장소의 설정이 각각 다르고 활성 로그는 즉시 제거되지 않을 수 있다. systemd가 실제로 적용한 값과 기존 로그 감소 시점은 실기기에서 확인해야 한다.
- `/diagnostics/memory`의 `disk`에 `totalBytes`, `freeBytes`, `legacyCopies`, `bytesByArea`, `lastCleanupAt`을 준다. 옛 설치 사본은 이름만 나열하며 지우지 않는다. 항목별 크기는 파일 길이의 합으로, 희소 파일이나 하드링크가 있으면 실제 디스크 점유량과 다를 수 있다. 심볼릭 링크를 따라가지 않고 최대 1만 항목까지만 센다. 권한 부족·누락·한도 초과는 0이 아닌 null이다.
- 암호화 원자료 백업은 임시 사본을 사용하므로 여유가 예약 공간 아래면 시작하지 않고 `backup_disk_low`를 반환한다. 백업 작업자는 대상 파일·SQLite 쓰기 로그·원자료 객체·첨부 임시 파일의 현재 크기를 합산한 세 배에 64MiB를 더해 예약하고 검증용 임시 복원도 같은 파일시스템에 둔다. 이는 추정이지 상한이 아니며, 과거 임시 백업이 현재 자료보다 매우 큰 경우의 계산은 별도 검증이 필요하다.
- 서버의 `disk_space::reserve(data_dir, requested_bytes)`는 대용량 쓰기 동안 반환된 잠금 객체를 보유한다. 동시에 다른 큰 쓰기가 들어오면 `reservation_busy`, 용량이 부족하면 `disk_low`다. 첨부 조각 쓰기와 완성 복사에 연결했다. `disk_space::active_reserved(data_dir)`는 진행 중인 예약 바이트를 돌려주며, 일반 쓰기는 고정 여유와 이 값을 합해 검사한다. 프로세스가 종료되면 파일 잠금이 운영체제에서 해제되어 남은 숫자를 진행 중인 예약으로 취급하지 않는다.
- S170 연결 계약: `data_dir/.momso-reservation-state.lock`을 짧게 배타 잠금한 뒤 `data_dir/.momso-reservation-operation.lock`을 비차단 배타 잠금한다. 빈 공간이 `1.5GiB + requested_bytes` 미만이면 거절하고, 충분하면 operation 파일을 0으로 자른 뒤 요청 바이트를 십진수와 개행으로 기록·동기화한다. state 잠금은 바로 놓고 operation 잠금은 **실제 큰 쓰기가 끝날 때까지** 잡는다. 두 파일은 서버 기동 시 자료 폴더 주인만 읽고 쓰도록 생성한다. 암호화 백업 작업자는 Python `reserve_large_write(data_dir, requested_bytes)`를 쓰며 업데이트 작업자는 같은 두 파일의 잠금을 사용한다. 업데이트는 풀 파일 크기와 자료 사본·복원용 복사에 필요한 크기를 합산한다. GitHub 동기화도 원자료 폴더를 제외한 자료·Git 기록과 채팅 DB 크기의 세 배에 64MiB를 더해 예약한다.
- 업데이트 롤백은 자료 폴더를 교체할 때 기존 잠금 파일 자체를 새 폴더로 옮겨 이미 보유한 예약을 유지한다. Linux에서 실제 파일과 별도 프로세스로 정상 교체, 세 교체 지점의 오류, 유지보수 해제 실패를 시험했다. 예약은 해당 업데이트 처리가 끝나면 해제되며, 갑작스러운 프로세스 종료가 각 파일 이동 순간에 일어나는 경우는 이 시험에 포함되지 않았다.
- 개발 Linux VM의 128MiB tmpfs에서 `small_filesystem_refuses_upload_and_keeps_reads_available`가 통과했다. 별도 2GiB tmpfs에서는 700MiB 시험 파일로 여유를 줄여 거절을 확인하고 그 시험 파일을 지운 뒤 첨부가 다시 되는 `full_filesystem_accepts_upload_after_space_is_freed`가 통과했다. 또 별도 2GiB tmpfs에서 오래된 가짜 브라우저 캐시를 자동 정리한 뒤 첨부 시작이 성공하고 가짜 쿠키가 남는 시험이 통과했다.

## 남은 일

- 개발 Linux VM의 실제 Chrome과 로컬 가짜 사이트로 로그인 쿠키를 만든 뒤 캐시를 정리하고 다시 열어 로그인이 유지되는 것을 확인했다. 실제 계정이나 실제 사이트는 사용하지 않았다.
- GitHub에서 받아 오는 원격 기록과 예전 임시 백업이 현재 자료보다 훨씬 큰 경우에는 현재 크기로 계산한 예약보다 더 필요할 수 있다. 이 추정은 실제 사용량의 상한이나 작업 성공을 보장하지 않는다. 일반 쓰기는 예약을 읽어 검사하지만 물리적 공간을 미리 할당하는 것은 아니므로 예약에 참여하지 않는 다른 쓰기와의 경합도 남는다.
- 업데이트 도중 중단된 복구 상태와 소유 표시가 없는 옛 판에 대한 실제에 가까운 정리 시험.

화면에서 정할 것: 디스크 부족을 어떻게 알리고 디스크 확장을 권할지.

## 이어받은 뒤 고친 것과 확인 (2026-11-25, 가지 `claude/anywhere-fixes`)

- **업데이트가 예약을 너무 일찍 잡던 결함**: 업데이트 작업자는 묶음을 받은 직후부터 큰 쓰기 예약을 쥔 채 문 닫기(유휴 대기)를 기다렸다. 진짜 server 는 `POST /maintenance` 때 새 백업을 시작하고, 백업 작업자(암호화 백업·GitHub 동기화)는 같은 예약을 잡아야 하므로 업데이트마다 그 백업이 `reservation_busy` 로 실패했다. 이제 묶음 풀기 동안만 예약하고(이때 판·자료 사본 둘을 합친 공간을 미리 확인) 놓은 뒤, 문이 닫히고 조용해지면 자료 사본·복원용으로 다시 예약해 업데이트 끝까지 쥔다. 두 번째 예약이 안 되면 문을 다시 열고 풀어 둔 판을 지운다. 시험 `test_update.py` 둘 추가(문 닫기 때 백업이 예약 가능, 두 번째 예약 실패 뒤 정리).
- **롤백 중 자료 폴더 교체와 예약 잠금**: `DataSnapshots.restore` 는 복사본을 만든 뒤 자료 폴더를 바꿔 끼운다. 잠금 파일도 함께 복사되므로 새 폴더의 두 잠금 파일은 일반 파일·링크 1개·주인만 읽기 쓰기로 유효하고, 업데이트가 끝나 잠금을 놓으면 다른 프로세스가 새 폴더에서 바로 예약할 수 있다(시험 `test_restore_during_held_reservation_leaves_usable_lock_files`, 별도 프로세스로 확인). 교체 뒤 업데이트가 쥔 잠금은 옮겨진 옛 폴더의 파일에 걸려 새 폴더를 막지 않는다. 롤백 뒤 업데이트는 큰 쓰기를 하지 않고 문 열기와 정리만 하므로 받아들인다. 교체하는 짧은 순간에는 자료 폴더가 없어 다른 예약이 `reservation_unavailable` 로 실패한다(안전한 쪽).
- **예약 크기 추정의 한계**: 여유 검사는 실제 빈 공간(`1.5GiB + 요청 크기`)을 보므로, 디스크에 남은 예전 임시 백업이 이미 차지한 공간은 검사에 반영된다. 남는 한계는 작업이 추정보다 많이 쓰는 경우(받아 오는 원격 Git 기록이 현재 자료보다 훨씬 큰 경우)다. 이때는 고정 여유 1.5GiB 를 파고든다. 정확한 상한은 **미확인**.
- **백업끼리의 예약 경합**: 문 닫기 뒤 암호화 백업과 GitHub 동기화가 함께 깨면 늦게 온 쪽이 `reservation_busy` 로 실패하고 30초 뒤 다시 돈다. 유휴 종료는 S174 의 기다림(기본 300초) 안에서 이를 기다린다.
- 합치기 때 생긴 `attachment_bridge.rs::fail` 의 `disk_low` 중복 갈래를 지웠다.
- S170 의 덜 올라온 조각 정리가 서버가 뜨는 순간 돌며 바쁨 표시를 켜서, 막 뜬 서버가 바쁨으로 보였다(서버 시험 `cancel_then_retry_keeps_one_user_message_and_replays_by_offset` 실패, 순번 9 통합 실행에서도 같은 실패). 첫 정리를 시작 5분 뒤로 미뤘다. VM 은 유휴 기준(30분) 동안은 떠 있으므로 정리는 여전히 돈다.
