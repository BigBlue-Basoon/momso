# 서버 브라우저 메모리 시험 (S155)

2026-11-25에 별도 시험 VM `momso-dev-deb12`의 Debian 12, 20GB 디스크에서 측정했다. 실제 계정이나 고객 자료는 쓰지 않았다. 설치기의 서버 설치 경로로 Chromium 156.0.8078.108을 설치했고 서버 상태가 정상이었다. 시험을 위해 SSH 사용자가 서비스 사용자와 같은 이름이어서 빈 자료 폴더는 시험 전에 만들었다.

## 측정 방법

제품의 headless Chromium 실행 경로와 채팅방별 프로필을 사용한다. 각 브라우저 프로세스 트리의 `/proc/<pid>/smaps_rollup` PSS를 합하고 `MemAvailable`을 읽었다. PSS는 공유 페이지를 나누어 계산한다. 시험용 작은 페이지와 3,000행 표 페이지이며 실제 바디코디 화면의 크기는 아니다. AI CLI는 VM에 설치되어 있지 않아 그 메모리는 포함되지 않았다.

설치된 서버 하나의 PSS는 19,968KiB였다. e2-small에서 가용 메모리는 브라우저를 띄우기 전 약 1.5GiB였다. 아래 수치는 브라우저 전체 PSS 합계 / 남은 메모리, 단위 MiB다. `됨`은 그 조합이 시험을 마쳤다는 뜻이며 실제 사이트에서의 안정성을 보증하지 않는다. 스왑 파일과 zram은 각각 2GiB였다.

4GB VM에서 서버 하나의 PSS는 17,356KiB였다. 이 부하에서 파일 스왑과 zram의 사용량은 각각 0이었다.

기본 크기는 **e2-medium을 권한다.** 시험한 큰 표 세 개 뒤 2GB VM에는 약 0.84~0.87GiB, 4GB VM에는 약 2.7GiB가 남았기 때문이다. 실제 바디코디, Codex·Claude CLI, 다른 작업이 동시에 차지하는 메모리는 아직 측정하지 않았으므로 최종 크기와 동시 사용 한도는 실제 사용 시험 뒤 본부가 정한다. 스왑은 이 시험의 작은 부하에서 뚜렷한 이점을 보이지 않았고, 메모리를 새로 만들어 주는 대안으로 볼 수 없다.

e2-small에서 S144의 실제 브라우저 시험 15개와 이 측정 시험 1개가 모두 통과했다. 사람 확인 요청, 인증번호와 저장된 로그인 선택은 휴대폰 크기의 가짜 화면과 서버를 통해 확인했다.

## 메모리 지킴이

서버는 새 브라우저를 띄우기 전에 `MemAvailable`을 확인한다. 기본 기준은 768MiB이고 `MOMSO_BROWSER_MIN_AVAILABLE_MIB`로 128MiB 이상으로 조정할 수 있다. 2GB VM의 큰 표 세 개 뒤 약 844~867MiB가 남았고 브라우저를 하나 더 띄우면 그만큼 줄어든다는 측정을 바탕으로 둔 보수적 시작값이다. 이 값은 실제 서비스의 안전 한도라고 확정된 값이 아니다.

부족하면 다른 채팅방 중 최근에 사용하지 않은 브라우저부터 닫고 다시 잰다. 실행 중인 요청은 닫지 않는다. 그래도 부족하거나 메모리를 읽을 수 없으면 `browser_memory_low`를 돌려준다. 닫은 방의 쿠키와 로그인은 프로필에 남지만 열린 페이지와 미저장 입력은 유지되지 않는다. 브라우저는 요청 중에 무한정 자랄 수 있고 다른 프로세스도 동시에 메모리를 쓸 수 있으므로 이 확인만으로 OOM을 완전히 없앨 수는 없다.

새 설치와 업데이트의 서버 서비스에는 `OOMScoreAdjust=-500`, 브라우저에는 `+500`을 적용한다. 이는 메모리가 고갈될 때 커널이 브라우저를 먼저 고를 가능성을 높이는 설정이며 서버 생존을 보장하는 설정은 아니다.
Debian Chromium은 시작 과정에서 상속한 점수를 0으로 되돌리는 것이 관찰되어, 브라우저 초기화가 끝난 뒤에도 점수를 다시 지정한다. Chromium 자식 프로세스의 점수는 엔진이 따로 정할 수 있다.
Debian의 실제 서비스 우선순위 `-500`으로 실행한 별도 systemd 시험에서도 브라우저 셋의 주 프로세스가 초기화와 페이지 이동 뒤 `+500`을 유지했다. 낮은 메모리 응답과 오래된 방 선택, 유휴 브라우저를 닫았다가 쿠키로 다시 로그인되는 시험도 통과했다.
