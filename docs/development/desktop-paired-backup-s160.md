# 데스크톱 묶음 백업과 복원

Git과 암호화된 앱 DB를 같은 묶음으로 기록하고, 두 쪽이 모두 확인된 묶음만 자동 복원 대상으로 삼는다. 저장된 로그인은 계속 백업하지 않는다.

진행 순서:

1. 다른 자료를 지우지 않는 충돌 선택 명령을 추가한다. 백업으로 바꿀 때는 현재 DB의 안전 사본을 먼저 만들고, 유지할 때는 아무것도 교체하지 않는다.
2. 자동 백업과 앱 종료 시점의 Git·DB 묶음 기록 및 완료 확인을 잇는다. 복구 키가 없으면 자동 DB 백업을 진행하지 않고 상태에 까닭을 남긴다.
3. 새 PC에서 완료된 묶음만 골라 Git과 DB를 맞춰 복원한다. 한쪽만 기록된 묶음은 건너뛰고, 사용자가 새로 만든 자료는 덮어쓰지 않는다.
4. 로컬 bare Git·가짜 객체 저장소로 정상 복원, 한쪽 실패, 종료, 복구 키 없음과 두 충돌 선택을 시험한다.

두 저장소의 쓰기에는 하나의 공통 트랜잭션이 없다. 한쪽 업로드만 성공한 상태를 성공으로 취급하지 않고, 완료 기록과 재시도를 통해 마지막으로 완성된 쌍을 보존해야 한다. 시험 전에는 이 문서를 완료 기록으로 취급하지 않는다.

Git만 연결된 경우에는 복구 키로 암호화한 DB를 조각으로 나누어 Git 객체에 넣는 길을 구현 중이다. GitHub 문서는 태그가 파일 객체(blob)를 가리킬 수 있다고 설명한다: [Git 태그 API](https://docs.github.com/en/rest/git/tags). 로컬 bare Git에서는 확인했으며, 실제 GitHub 계정에 쓰는 시험은 하지 않았다. 원자료 파일은 기존처럼 별도 저장소에 둔다.

완료 묶음의 Git 태그에는 묶음 번호와 생성 시각을 기록하고, 암호화된 DB 기록의 번호·시각 및 Git 버전과 대조한다. Git 전용 DB의 조각과 완료 기록은 각각의 Git 참조에 보관하며, 완료 기록은 마지막에 올린다. 새 묶음이 완성되기 전에는 이전 묶음을 지우지 않는다. 오래된 묶음과 실패한 조각의 보관 기간·정리 방식은 아직 정하지 않았다.

자동 실행과 종료 경로에 연결했다. Git이 켜져 있으면 Git 업로드 후, 원자료 자동 업로드가 켜져 있으면 그 업로드 후 DB 사본을 만든다. 종료 시에도 실행한다. DB는 복구 키로 암호화하며 키가 없거나 아직 확인되지 않았으면 DB를 올리지 않는다. Git만 연결된 경우에는 암호화한 DB 조각을 Git 참조에 올린다. 원자료 저장소만 연결된 경우에는 암호화한 DB를 그 저장소에 올린다.

완료 기록은 해당 Git 버전과 DB 업로드가 끝난 뒤에만 쓴다. 복원은 묶음 번호·시각·Git 버전·DB 사본을 대조하고, 더 새 묶음이 미완성이거나 손상됐다면 앞의 완전한 묶음을 고른다. 묶음용 DB 사본은 예전 단독 백업과 구분하므로 완료 표시가 없는 새 DB가 단독 백업으로 선택되지 않는다. 오래된 단독 백업에는 원래부터 묶음 기록이 없으므로 과거의 Git과 DB가 같은 시점인지는 증명할 수 없다.

종료는 기존 20초 제한 안에서 백업을 시도한다. 연결 장애나 큰 자료 등으로 그 안에 끝나지 않으면 종료 시 최신 백업이 완료됐다고 보장할 수 없다. 성공한 이전 묶음은 유지되며 다음 실행에서 다시 시도한다. 백업 실패와 진행 상태를 종료 전에 사용자에게 어떻게 알릴지는 화면에서 정해야 한다.

충돌 선택 명령: `app_state_restore_use_backup()`은 DB 교체 전 현재 DB의 안전 사본을 남기고 `app_state_restore`와 같은 결과를 반환한다. 추적 중인 로컬 Git 변경과 기존 이력도 로컬 안전 참조로 남긴다. `app_state_restore_keep_current()`는 현재 상태를 건드리지 않고 `{state: "kept"}`를 반환한다. 화면은 사람이 선택한 뒤에만 해당 명령을 불러야 한다. 원자료 파일은 이 명령들이 지우지 않는다. Git이 추적하지 않는 파일과 복원할 파일의 경로가 겹치거나 심볼릭 링크 등 안전하지 않은 경로가 있으면 명시적 선택이어도 `local_data_conflict` 또는 `unsafe_path`로 멈춘다. 자동으로 그 파일을 옮기거나 지우지 않는다.

화면에서 정할 것: `archive_auto_backup_get` 또는 `object_store_auto_upload_get`의 `reason`이 `recovery_key_missing`이나 `recovery_key_unconfirmed`일 때 복구 키 설정을 안내한다. `backup_original_missing`은 DB가 참조하는 원자료의 백업 조각이 부족함을 뜻한다. 복원 결과에는 새 선택 필드 `bundleId`가 있을 수 있다. `backup_pair_incomplete`, `local_data_conflict`, `unsafe_path`, `restore_busy`, `restore_recovery_pending`, `restore_recovery_conflict`에 맞는 안내와 두 선택을 보여 줄 곳을 정한다. 새 PC에서는 복구 키를 입력하고 GitHub·원자료 저장소를 다시 연결해야 한다. 저장된 로그인과 AI 공급자 자격 증명은 백업되지 않으므로 다시 입력한다.

Git만 연결된 경우에는 복구 키를 넣은 뒤 `app_state_restore()`를 직접 호출할 진입점이 필요하다. 기존 `storeRestore` 화면 함수는 뒤이어 원자료 저장소 복원도 호출하므로, 저장소가 연결되지 않은 Git 전용 상황에는 그대로 쓸 수 없다. Git 전용 DB 백업에는 원자료 파일이 들어 있지 않으므로 별도 저장소가 없으면 파일은 돌아오지 않는다는 안내도 필요하다.

검증: 로컬 bare Git·로컬 가짜 객체 저장소에서 `automatic_pair_backup_and_new_profile_restore`는 자동 백업, 종료 시 백업, Git만 먼저 바뀐 경우 이전 묶음 선택, 새 프로필의 대화와 첨부 SHA-256, 충돌 뒤 두 선택과 안전 DB 사본을 검사했다. `paired_git_store`는 Git 전용 암호화와 미완성 새 묶음 건너뛰기를, `paired_restore`는 다른 이력과 중단 복구를 검사했다. 기존 복원 17개, 묶음 관련 7개, 객체 자동 업로드 2개, Git 자동 백업 4개(로컬 원격을 쓰는 두 시험 포함)도 통과했다. 실제 GitHub·R2·새 PC의 화면은 시험하지 않았다.
