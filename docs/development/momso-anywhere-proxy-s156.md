# S156 프록시 갱신 확인

검증은 가짜 공급자와 리눅스 시험 환경에서 수행했다. 실제 고객 설치의 재시험은 아직 하지 않았다.

- 순번 7의 실제 장애: PC 설치 후 updater 설치가 프록시 두 파일만 현재 릴리스에 기록했고, 기존 baseline 이동도 두 파일만 복사했다. 프록시가 가져오는 나머지 모듈이 없어 서비스가 시작되지 않았다. 설치기의 기존 서버 health는 프록시나 입구를 통과하지 않았다.
- 프록시 파일 목록은 `scripts/momso_anywhere_proxy_files.json`이다. PC 설치·갱신, baseline, 서명 묶음, VM 작업자와 휴대폰 시작이 이 목록을 사용한다. 이미 있는 동일한 파일은 관리 기록에 편입하고, 알 수 없는 다른 내용은 덮지 않는다.
- 기존 PC 설치를 올릴 때 프록시 교체, 작업자 설치와 입구를 통과한 검증을 서버·자료 복구 지점 안에서 진행한다. 작업자가 없는 설치는 그 안에서 baseline을 처음 만든다. 검증이 실패하면 이전 입구와 파일을 복구하고 새로 만든 baseline도 정리한다. 이 경로는 유지보수 문이 닫혀 있는지 확인한다.
- 새 입구는 VM과 입구가 공유한 비밀값으로 계산한 검증값을 요구하는 `/__momso/proxy-health`를 제공한다. 이 요청은 입구와 프록시를 거쳐 서버 `/health`를 확인하며, 앱은 검증값을 기록하거나 URL에 넣지 않는다. 설치기와 VM 작업자는 프록시 상태와 이 경로를 확인한다. 입구 이미지가 바뀌므로 새 서명 릴리스와 이미지가 필요하다.
- 휴대폰 시작은 고객의 Google 권한으로 이 설치의 전송 비밀값을 읽어 브라우저 메모리에서 검증값을 계산한다. 비밀값과 검증값은 저장소나 주소에 보관하지 않는다. 입구의 교차 출처 요청은 설정된 로그인 출처만 허용한다.
- VM 작업자는 서버가 바빠 `busy`로 반환되면 기본 1시간 대신 5초 뒤 재확인한다. PC가 이미 같은 순번을 기록했다면 유지보수 문이 풀린 뒤 다시 읽고 기존 복구 기록을 건드리지 않는 범위에서 `up_to_date`로 맞춘다. 실제 14분 대기의 직접 원인은 해당 시점의 활동·잠금 기록을 확인하지 못해 확정할 수 없다.
- PC의 기존 갱신은 현재 릴리스 디렉터리 내용을 교체하므로 디렉터리 이름 자체는 옛 순번을 계속 가리킬 수 있다. 설치된 순번은 `installed.json`과 작업자 상태로 확인하며 디렉터리 이름만으로 판정하지 않는다.
- 새 설치의 최종 검증이 실패하면 이번 실행에서 만든 것으로 확인한 입구를 제거한다. VM과 나머지 설치 자원은 자동으로 버리지 않으므로 재시도하거나 설치 기록을 이용해 정리해야 한다.
- S117a는 알려진 실패 코드와 설치기에서 나온 안전한 `실패:` 문장을 전달한다. 토큰·비밀번호·URL 등이 포함될 가능성이 있는 임의 표준 오류는 출력하지 않는다.
- 가짜 시험과 실제 클라우드 확인은 다르다. 실제 고객 입구와 휴대폰 확인은 새 이미지 발행 후 별도로 해야 한다.
