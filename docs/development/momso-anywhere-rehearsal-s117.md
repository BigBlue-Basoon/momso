# S117 실제 설치·복구 시험 준비 상태

## PC 실행기 (S117a)

`scripts/momso_anywhere_rehearsal_s117a.py`는 PC 설치기 `anywhere`와 `destroy`를 차례로 호출한다. 실제 실행은 본부가 한다. 다른 설치와 프로젝트 자체를 지우지 않는다. `--protect-installation-id`를 여러 번 주면 그 설치를 보호하고, 주지 않으면 프로젝트의 VM과 모든 지역의 Cloud Run 목록을 읽어 기존 설치를 보호한다. 목록을 읽을 수 없으면 시작하지 않는다. 서명된 목록과 로컬 묶음의 일치도 기존 검증기로 먼저 확인한다. Google 로그인 값 세 개는 실행자가 인자로 준다. Cloud Run 전체 지역 조회는 [Google 공식 v1 목록 API](https://docs.cloud.google.com/run/docs/reference/rest/v1/namespaces.services/list)를 사용한다.

```powershell
python scripts/momso_anywhere_rehearsal_s117a.py --account <계정> --project <프로젝트> --release-manifest-url <서명목록주소> --bundle <묶음폴더> --public-key <공개키파일> --channel <production또는development> --google-client-id <Google로그인앱ID> --owner-sub <소유자번호> --login-origin <로그인출처>
```

묶음 폴더에는 `momso-server`와 `web.tar.gz`가 있어야 한다. 서버·화면 파일의 지문은 직접 계산하고 서명된 묶음과 대조한다. 실제 확인은 입구 트래픽을 받는 판의 이미지 지문, 로그인 전 HTTPS, VM의 네 서비스, VM 내부에서 인증한 `/update/status`다. 로그인·토큰 값과 명령 원문은 출력하지 않는다. 유휴 종료·재기동·휴대폰 브라우저 검사는 포함하지 않는다.

설치 중 또는 검사 중 실패해도 기존 삭제기를 실행하고, 이 시험 ID와 라벨이 일치하는 시험용 백업 버킷만 별도 정리한 뒤 목록을 조회한다. 버킷 정리가 성공하고 키 이름과 소유 라벨이 확인되면 시험용 키 버전의 파기를 예약한다. 조회 오류, NAT·IAM의 중첩 범위, 다른 지역의 입구, 버킷의 보호된 삭제본은 `미확인`으로 보고한다. KMS 파기 예약은 비용이 남는 상태와 예정 시각을 표시한다. 삭제기 실패나 백업 정리 실패는 오류로 끝난다. 상태 파일은 재확인을 위해 임시 폴더에 남기며 파일 경로만 출력한다. 강제 종료나 전원 차단으로 정리 절차가 실행되지 않을 수 있으므로, 그때는 남은 상태 기록과 소유권을 직접 확인해야 한다.

아래는 앞선 조사 기록이며 실행기의 현재 상태 설명은 이 절이 우선한다.

### 선택 확인: 유휴 종료와 다시 켜기 (S117b)

위 명령 끝에 `--check-idle`을 붙이면 처음 네 확인이 통과한 뒤 시험 VM에만 유휴 60초·검사 간격 5초를 적용한다. 운영 기본 1800초와 배포 파일은 바꾸지 않는다. 서버가 작업과 켜진 백업을 안전하게 마쳐야 실제로 꺼진다. 종료까지 15분, 로그인 뒤 켜짐과 준비까지 15분을 기다린다. 실패해도 기존 정리 절차는 실행한다.

서버에서는 유지보수에 들어가기 전의 종료 가능 여부와 들어간 뒤의 정리 완료 여부를 분리했다. 이 수정이 들어간 서명된 서버 묶음을 배포해야 고쳐진 서버를 실제로 시험할 수 있다. 이전 묶음으로 실행하면 이전 동작을 시험한다.

공개 `/__momso/ready`는 입구 상태만 알려 주며 VM을 깨우지 않는다. 로그인하지 않은 `/`도 로그인 화면을 안내할 뿐이다. 스크립트는 두 응답의 상태 코드와 종류를 기록하고 시험 주소를 표시한다. 사람이 휴대폰에서 주소를 열고 로그인하면 입구가 VM을 깨우며, 스크립트는 VM 상태와 인증된 내부 `/health`의 `ready`, 이 시험 입구 서비스 계정이 시작한 새 VM 시작 작업을 확인한다. 시작 작업 조회 권한이 없거나 실행 주체를 확인할 수 없으면 성공으로 치지 않는다. `wakeSeconds`는 로그인 대기까지 포함한 시간이다. 로그인 완료 전에는 자동 깨우기를 성공으로 표시하지 않는다. 로그인 후 사용자가 본 화면의 실제 응답은 이 스크립트가 읽을 수 없으며 `ownerResponse: unobserved`로 남긴다. 사람이 확인한다. 기존 입구의 가짜 시험에서는 깨우는 동안 HTTP 200의 HTML 안내 화면이 나온다.

출력의 `stage`는 실패한 단계다. 종료가 시간 안에 일어나지 않으면 서버의 작업·백업 준비 상태 중 민감하지 않은 값만 보여 준다. 실제 계정·세션·토큰은 수집하거나 출력하지 않는다. 이 검사는 시험용 부품의 가짜 시험이며, 실제 VM의 종료·재기동은 본부가 실행해 확인해야 한다.

## 이전 상태: 실행 준비 미완료

### PC 확인 부품의 추가 현황 (S117a)

`scripts/momso_anywhere_rehearsal_s117a.py`에는 입구의 실제 트래픽 판·지문과 공개 HTTPS, 네 서비스와 인증된 업데이트 상태를 확인하는 읽기 전용 함수가 추가됐다. 보호 설치 ID는 조회 전에도 거절한다. PC 자원 목록과 서울 지역 백업 키 버전 조회의 일부도 가짜 응답으로 시험했다. 조회 실패·다른 지역·중첩된 IAM/NAT는 확인되지 않은 상태다. **이 부품은 아직 설치기·삭제기와 연결된 실행 명령이 아니며, 자원이 전부 없어졌다는 증거가 아니다.**

PC 설치기는 배포 목록·묶음·공개키 외에 Google 로그인 앱 ID, 소유자 번호, 로그인 출처도 요구한다. 실제 실행기는 이 값을 신뢰할 수 있는 입력에서 받아야 한다. 삭제 실패와 프로세스 중단 뒤 재시도를 위한 소유권 기록, 시험용 백업의 안전한 정리, 모든 자원과 IAM의 완전한 조회도 남았다.

[Google Cloud 요금표](https://cloud.google.com/kms/pricing)는 사용 중·사용 중지·파기 예약인 키 버전을 과금 대상으로, 파기 완료된 버전을 무료로 구분한다. [KMS 삭제 안내](https://docs.cloud.google.com/kms/docs/delete-kms-resources)에 따르면 키와 키링은 하위 자원 등 조건이 충족돼야 삭제할 수 있다. 그러므로 파기 예약과 이름이 남은 상태를 별도로 보고해야 한다.

실제 클라우드에서 실행할 명령은 아직 제공하지 않는다. 실제 프로젝트·설치를 바꾸거나 계정 토큰을 읽지 않았다. `scripts/momso_anywhere_rehearsal_s117.mjs`는 실행기가 아니라 **가짜 어댑터로만 시험한 공통 순서 함수**다. `node --test scripts/test_momso_anywhere_rehearsal_s117.mjs`는 로컬 가짜 시험이며 실제 설치·삭제를 하지 않는다.

공통 틀은 새 24자리 ID의 앞 12자리가 보호 ID와 같으면 시작 전에 거절하고, 시작 중 실패해도 삭제 함수를 호출한 다음 자원 확인 함수를 호출한다. 확인 항목 6개가 전부 `passed`이고 필수 자원 항목 14개가 전부 `absent`이며 삭제 결과가 `done`일 때만 완료다. 누락·접근 불가·남은 자원은 완료가 아니다. 오류 원문이나 어댑터의 임의 상세는 결과에 넣지 않는다. 단, **현재 전달되는 어댑터는 가짜뿐이므로 이것이 실제 소유권 확인이나 실삭제를 보장하는 것은 아니다.** 프로세스 강제 종료·전원 중단에서는 `finally`가 실행된다는 보장도 없다. 실제 실행기에는 독립적인 재실행 가능한 정리 기록이 필요하다.

같은 모듈의 `googleBrowserInventory`는 브라우저 경로의 이름별 읽기 전용 조회 초안이다. 실제 API 호출은 하지 않았고 가짜 응답으로만 시험했다. 목록 권한을 별도로 증명하지 못하므로 404와 403을 모두 `unknown`으로 두며 IAM도 `unknown`으로 남긴다. 따라서 이를 실제 자원이 0개라는 증거로 사용할 수 없다. PC 설치기의 다른 이름은 아직 다루지 않는다.

`scripts/momso_anywhere_test_backup_cleanup_s117.mjs`는 시험 ID·보호 ID·새로 만든 자원이라는 별도 증명 함수, 버킷과 키의 소유 라벨을 확인한 뒤 버킷 객체 삭제와 키 버전 파기 예약을 요청하는 **미연결 부품**이다. 실제 인증 전송기·신규 설치 증명·재시도 기록이 없어 본부가 실행할 명령이 아니다. 가짜 API에서만 확인했으며 실제 버킷이나 키를 건드리지 않았다. `DESTROY_SCHEDULED`는 `may_be_billable`로 보고한다. 일반 고객의 기본 삭제는 그대로 백업을 보존한다. 고객용 '전부 지우기'에 필요한 동의 화면·복구 불가 경고·비용 및 보존 안내는 화면 담당과 본부가 정해야 하며, 제품 삭제기 옵션은 아직 연결되지 않았다.

## 확인한 차이와 잔여 위험

1. PC 설치기 `scripts/momso_server_install.py::initialize_state`는 12자리 ID를 상태 파일에 만들고, 휴대폰 REST `scripts/momso_anywhere_setup.mjs::startAnywhere`는 24자리 ID를 사용하되 자원 이름에는 앞 12자리를 쓴다. 두 경로를 동일한 이름 규칙이라고 간주하면 안 된다. 새 상태 파일·기존 설치 ID 목록·충돌 검사와 자원별 소유 표식 검사가 필요하다.
2. 브라우저 `scripts/momso_anywhere_google_browser.mjs::destroy`의 삭제 목록에는 백업 버킷과 KMS 키링이 없다. PC 기본 삭제도 백업 자료를 보존하는 기존 결정이 있어 삭제 성공만으로 자원 0개라고 말할 수 없다. 백업 버킷은 실제 시험 ID의 소유 표식과 데이터가 오직 이번 시험 것임을 확인한 뒤에만 별도 삭제해야 한다. 기존 설치의 백업은 절대 건드리지 않는다.
3. [Google 공식 KMS 문서](https://docs.cloud.google.com/kms/docs/key-states)에 따르면 키 버전 파기는 예약 상태를 거치며 기본 30일, 일반 키 최소 24시간이다. **파기 예약 상태도 과금 대상이다.** `DESTROYED`가 된 버전만 무료라는 [공식 요금표](https://cloud.google.com/kms/pricing)의 설명은 본부가 전달한 "예약 즉시 과금 없음"과 다르다. 또한 현재 [리소스 삭제 문서](https://docs.cloud.google.com/kms/docs/delete-kms-resources)에 따르면 조건을 충족하는 키 버전·키·키링은 삭제할 수 있어 "영영 지울 수 없음"으로 단정할 수 없다. 실제 계정에서 기능·권한을 검증하지는 않았다. 시험 종료 직후 과금 자원 0개라는 판정은 보장할 수 없으며, 예약·파기 완료·삭제 가능 여부와 비용 가능성을 따로 추적해야 한다. 실제 키 파기는 복원 불가하므로 소유 확인 없는 자동 실행을 해서는 안 된다.
4. 서버리스 주소가 회수되지 않으면 서브넷·네트워크 삭제가 미뤄질 수 있다. 각 자원의 조회가 403이거나 실패한 경우에는 없는 것으로 판단하지 않는다. 계정별 IAM 결합, NAT, 디스크와 비밀, 버킷과 KMS도 읽기 권한이 있어야 확인할 수 있다.
5. `scripts/momso_anywhere_gateway.py`의 공개 `/__momso/ready`는 입구 프로세스만 확인한다. `/update/status`는 `scripts/momso_anywhere_vm_proxy.py`의 인증 보호 경로이며, 별도 인증 없이 200으로 판정할 수 없다. VM의 실제 `momso-server`, `momso-private-proxy`, `momso-idle-stop`, 업데이트 서비스는 설치된 서비스 이름과 상태를 각각 확인해야 한다.
6. 유휴 종료는 단순 대기만으로 보장되지 않는다. `apps/alpha/desktop/src-tauri/momso-idle-stop/idle_stop.py`는 서버의 `shutdownReady` 등 조건을 확인한다. 백업 준비가 미완료면 종료되지 않을 수 있다. 꺼진 뒤 깨우기도 인증된 경로와 실제 VM 상태 변화를 함께 확인해야 한다. 사용자 세션·비밀을 출력하거나 보호된 확인을 우회하지 않는다.

## 실제 어댑터에 남은 필수 작업

- PC `anywhere`와 `destroy` 실행을 명시적 계정·프로젝트와 새 전용 상태 파일에 연결하고, 설치가 중간에 실패해도 소유 확인 후 정리한다. 배포 목록 서명과 지문을 기존 설치기에서 검증한다.
- 브라우저 REST 공급자에 토큰을 표준입력 등 안전한 경로로 주고 기존 프로젝트·새 24자리 ID를 사용해 `startAnywhere`와 소유 확인된 `destroy`를 호출한다. 토큰·비밀·HTTP 원문을 출력하거나 상태 파일에 저장하지 않는다.
- 트래픽을 받는 판의 실제 지문, 공개 HTTPS, 네 서비스, 인증된 `/update/status`, 실제 유휴 종료와 재기동을 각각 기계적으로 확인한다. 미확인은 미확인으로 남긴다.
- VM·디스크·네트워크·서브넷·방화벽·라우터·NAT·Cloud Run·서비스 계정·역할·비밀·IAM·백업 버킷·KMS를 소유 표식과 정확한 ID로 조회하고, 404와 403을 구분한다. 각 삭제의 실패·지연·보존 사유를 남긴다. 다른 설치·프로젝트 자체는 수정하지 않는다.
- 가짜 Google로 충돌, 설치 중 실패, 403, 남은 버킷·키, 정리 실패와 재시도, 토큰 비출력을 시험한 후에만 본부의 실제 명령을 제공한다. 실제 IAM·API 권한과 서명된 순번 5 묶음은 본부가 확인한다.

## 충실도 확인
