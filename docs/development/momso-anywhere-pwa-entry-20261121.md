# 휴대폰 홈 화면과 몸소 입구

확인일: 2026-11-21. 제품 안에서 보이는 이름은 **momso**, 문장 안에서는 **몸소**다. 별도 몸소 아이디·비밀번호를 만들지 않는다. 현재 첫 판은 VM을 만든 Google 계정 하나가 주인이고, 고객마다 고객 프로젝트의 `run.app` 입구가 다르다. **가짜 서비스로 시험한 설계이며 실제 iPhone·Android와 실제 계정 확인은 아직 하지 않았다.**

## 홈 화면과 로그인

Apple은 iOS/iPadOS 17.2부터 웹 앱을 홈 화면에 추가할 때 브라우저의 해당 사이트 쿠키를 한 번 복사하지만, 그 뒤 브라우저와 홈 화면 앱의 쿠키·저장소는 별개라고 설명한다. 다른 로컬 저장소는 복사되지 않는다. 그러므로 복사된 쿠키가 없거나 만료되면 홈 화면 안에서 Google로 다시 로그인한다. 이미 다른 앱이나 Safari에서 로그인했다는 이유만으로 홈 화면 앱에서도 로그인되었다고 가정하지 않는다. [Apple WebKit: 로그인 쿠키](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/).

개발 코드에서는 로그인하지 않은 입구가 공통 로그인 페이지로 전체 화면 이동한다. Google OIDC의 ID 토큰은 fragment로 돌아오고, 공통 페이지와 고객 입구는 각자 fragment를 즉시 주소에서 지운다. 입구는 Google 서명·대상·주인 `sub`·원래 challenge의 nonce를 확인한 뒤 세션 쿠키를 만든다. `window.open`과 `opener`는 사용하지 않는다. 다른 출처의 인증 화면에 출처·주소 표시가 보이는 것은 정상이며 숨기거나 다른 주소처럼 보이게 하지 않는다. **전체 화면 복귀·referrer·sessionStorage·쿠키가 실제 iPhone 홈 화면에서 작동하는지는 미검증**이다. 기존에 배포된 입구에는 이 변경이 아직 적용되지 않았다. [Apple WWDC: 범위와 로그인](https://developer.apple.com/videos/play/wwdc2023/10120/).

세션은 고객 입구의 `__Host-momso-session` 쿠키에만 두며 `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`를 쓴다. 발급 시각 기준 최대 30일이며 앱을 닫았다 다시 열어도 쿠키가 살아 있으면 매번 로그인하지 않는다. 이는 자동 갱신이 아닌 절대 만료다. 기기 분실이나 Google 계정 접근 철회가 발생해도 기존 쿠키가 즉시 취소되지는 않는다. 현재는 입구의 고객 소유 세션 서명 키를 바꾸면 모든 기기를 로그아웃할 수 있고, `POST /__momso/auth/logout`은 현재 기기의 쿠키를 지운다. 기기별 폐기와 사용자별 권한은 아직 없다. 공유 기기·잠금 해제된 기기에서는 30일 세션의 위험을 알려야 한다.

## 설치 파일과 안전 경계

로그인 전에도 다음 **고정된 파일만** 입구가 제공한다: `/manifest.webmanifest`, `/app-icons/apple-touch-icon.png`, `/app-icons/favicon-32.png`, `/app-icons/icon-192.png`, `/app-icons/icon-512.png`, `/app-icons/icon-512-maskable.png`. 로그인 페이지에는 매니페스트(`crossorigin=use-credentials`)와 Apple 아이콘 링크가 있다. 이 파일들은 사용자의 문서·사진·대화가 아니라 제품 빌드의 공개 자산이며, 입구 이미지에 포함되어 VM이 꺼져도 제공된다. 다른 화면 파일 전체나 API, 임의 경로는 공개하지 않는다. 화면 정적 파일 전체 공개도 비밀이 없는 빌드라면 가능하지만, 설정·사람 자료가 섞일 위험과 점검 범위를 줄이기 위해 여기서는 선택하지 않았다.

PC 설치는 지정한 화면 tar.gz에서 이 여섯 파일만 확인해 Cloud Run 소스에 넣는다. 휴대폰 설치의 입구 이미지는 `python scripts/prepare_momso_anywhere_image.py --web "<화면 빌드 폴더>" --output "<새 이미지 빌드 폴더>"`로 맥락을 준비하고, 그 폴더를 컨텍스트로 `scripts/momso_anywhere_image/Dockerfile`을 빌드한다. 매니페스트의 시작 주소·범위와 아이콘 경로, PNG 표식을 확인하고 누락·중복·외부 경로면 설치를 진행하지 않는다. 화면 쪽의 `manifest.webmanifest`와 아이콘이 바뀌면 입구 이미지도 함께 다시 빌드해야 한다.

스냅샷 `a74c6ff`의 매니페스트와 아이콘 여섯 파일은 저장소 객체에서 읽어 위 검사를 통과했다. 앱 빌드와 입구 이미지에 실제로 복사되어 휴대폰에서 설치되는지는 별도 확인이다.

## 주소를 잊었을 때

시작하기·내 몸소 찾기·공통 로그인의 확정된 공통 출처는 `https://anywhere.momso.yoga`다. 로그인은 `https://anywhere.momso.yoga/`, 시작·찾기는 `https://anywhere.momso.yoga/start/`에 두며, 소개 사이트는 시작 주소로 가는 링크만 제공한다. 주소 확정은 DNS·게시 완료를 뜻하지 않는다. 시험에는 별도 Cloud Run 기본 `run.app` 주소를 먼저 쓴다. 실제 OAuth 등록·휴대폰 시험은 아직 하지 않았다. 구체적인 정적 파일 배치와 서로 다른 출처를 쓰는 경우는 [시작 화면 게시 계약](momso-anywhere-onboarding-s26.md#시작-화면-게시-계약)을 따른다.

**선생님마다 다른 주소:** 각자의 Google 프로젝트에서 만든 Cloud Run 입구에 Google이 HTTPS 주소를 준다. 한 형태는 `https://<서비스이름>-<프로젝트번호>.<지역>.run.app`이고, 다른 형태는 `https://<Google이 정한 식별자>.run.app`이다. 어느 주소가 실제 반환될지는 설치 때 Google 응답을 따르며, 무작위 식별자 부분을 추측하거나 분해하지 않는다. Cloud Run 서비스가 유지되는 동안 주소는 안정적이지만, 서비스·프로젝트·지역을 바꿔 다시 만들거나 기본 주소를 끄면 예전 주소를 계속 쓸 수 있다고 가정하지 않는다. 몸소는 시작 완료 때 그 주소를 보여 주고, 나중에 공통 시작 페이지의 **내 몸소 찾기**로 다시 찾는 것을 목표로 한다. 현재 찾기는 휴대폰 설치가 표시한 프로젝트와 알려진 입구 이미지를 찾는 범위이며 실제 계정 시험은 아직 없다. 나중에 더 읽기 쉬운 주소를 붙이려면 도메인 소유 확인, DNS·HTTPS 인증서와 고객 입구로 보내는 설정이 필요하다. 선생님 자신의 도메인을 각자 연결할 수도 있고, 우리가 관리하는 도메인 아래 하위 주소를 나눠 줄 수도 있다. 후자는 우리가 주소 발급·DNS와 그 유지 관리를 맡는 구조이지만, 반드시 고객 서버나 대화 내용을 우리 서버로 중계해야 하는 것은 아니다. 어느 방식을 쓸지는 정해지지 않았고 현재 코드는 고객별 사용자 지정 주소를 지원하지 않는다. [Cloud Run 서비스 주소](https://docs.cloud.google.com/run/docs/triggering/https-request), [사용자 지정 도메인](https://docs.cloud.google.com/run/docs/mapping-custom-domains).

시작 화면 담당은 `findFromGesture({google, clientId, release})`를 Google 로그인 단추의 직접 동작에서 호출한다. 고객이 Google 권한을 승인하면 브라우저가 고객 계정으로 볼 수 있는 Google 프로젝트 중 몸소 설치 표시가 붙은 것만 검색하고, 입구의 주인 `sub`, 로그인 앱 ID, 신뢰하는 이미지 지문, 최신 실행 판과 `run.app` 주소가 일치하는 것만 URL 목록으로 돌려준다. 여러 개면 화면에서 선택하게 한다. 접근 토큰은 브라우저 메모리에만 있고 우리 쪽 서버로 전달하지 않는다. Google 프로젝트 검색은 결과가 늦게 반영될 수 있다. [Google 프로젝트 검색](https://docs.cloud.google.com/resource-manager/reference/rest/v3/projects/search).

이 복구는 접근 가능한 활성 프로젝트에서 휴대폰 설치의 입구 표시를 찾는다. 기존 프로젝트에 휴대폰으로 설치한 경우도 포함한다. 예전 PC 명령으로 설치한 경우, 고객이 해당 프로젝트의 Cloud Run 조회 권한을 잃은 경우, 신뢰 이미지 목록에 이전 판이 없는 경우에는 못 찾을 수 있다. 공개 시작 페이지의 `release`에는 현재 `gatewayImage`와 필요 시 과거 정상 판의 지문 배열 `trustedGatewayImages`를 포함한다. 고객 브라우저 저장소가 지워져도 검색은 가능하지만, 검색·가입 권한을 거부했거나 Google 서비스가 불안정하면 안내 후 다시 시도해야 한다. 실제 Google 계정 검색은 미검증이다.

## 여러 사람

지금은 `MOMSO_OWNER_SUB` 한 사람만 받는다. 나중에는 주인이 승인한 Google `sub`별 허용 목록, 역할·자료 범위, 초대·제거, 기기 세션 폐기와 감사 기록을 고객 프로젝트에 두는 방향으로 확장한다. 이메일 표시만으로 신원을 확정하거나 다른 강사에게 VM 전체 관리 권한을 자동 부여하지 않는다. 구성원용 주소 찾기와 권한 철회 후 기존 30일 쿠키의 즉시 차단도 별도로 구현해야 한다. **현재 강사 계정은 아직 로그인할 수 없다.**

## 화면 계약

- 로그인 전 일반 API `fetch`는 `401`, `application/json`, `{"error":"login_required"}`, `Cache-Control: no-store`다. 화면은 이 값을 받고 입구 로그인 화면으로 돌아간다.
- 개발 코드에서 브라우저가 문서 탐색으로 연 입구는 로그인 전 글자 없는 `200` 페이지를 거쳐 공통 로그인 페이지로 이동한다. JSON 응답을 기대한 자리에서 HTML이 오거나 다른 출처로 이동하면 화면은 정상 데이터로 취급하지 않는다. 실제 배포 반영은 별도로 확인한다.
- 잘못된 출처·로그인 증명은 `403`이다. 현재 입구가 로그인 완료 `POST /__momso/auth/finish`를 거절하면 JSON `{"error":"login_failed"}`를 준다. Host 검사 또는 변경 요청의 Origin 검사 거절은 `403` HTML이며 통일된 JSON 까닭 값은 없다. 입구 뒤 서버가 다른 `403`을 돌려줄 가능성도 있다. 화면은 `403`을 전부 로그인 만료로 간주하지 않고 **닿지 못했거나 요청이 거절됨**으로 안내한다. `login_failed`도 계정 불일치·만료된 로그인 시도 등 어느 한 원인으로 단정하지 않는다. 구체적인 까닭 값의 통일은 아직 구현되지 않았다. VM 통신 실패는 `503`이고, 로그인된 사용자의 첫 문서 탐색에서 VM이 꺼져 있으면 켜는 동안 5초 자동 새로고침 안내를 준다.
- 사용자가 명시적으로 로그아웃할 때 `POST /__momso/auth/logout`을 같은 출처에서 부른다. 쿠키는 브라우저가 지운다. 로그인 중·로그아웃·만료 상태에서 토큰 값을 화면이나 기록에 남기지 않는다.

## 실제 휴대폰에서 확인할 것

1. iOS 17.2 이상과 현재 iOS의 Safari에서 로그인 전 홈 화면에 추가: 이름·아이콘·독립 창, `crossorigin=use-credentials` 매니페스트와 아이콘 로드.
2. 앱 설치 전 로그인 쿠키 복사 여부와, 설치 후 Safari와 앱에서 각각 로그인·로그아웃했을 때 분리 여부.
3. 홈 화면 앱에서 Google 전체 화면 이동·주소 표시·계정 선택·원래 앱 복귀와 referrer 누락·sessionStorage 제한 시 안내.
4. 앱 종료·재실행과 날짜 경과 뒤 세션 유지, 만료·키 교체·로그아웃 뒤 화면 반응. 실제로 30일 동안 기다린 시험은 아직 없다.
5. VM이 꺼진 상태에서 앱 아이콘·로그인 화면을 확인하고 다시 열어 자동 깨우기·채팅·끊긴 SSE 재접속 확인.
6. Google 재로그인으로 잊은 주소 찾기, 복수 고객 프로젝트·접근 권한 상실·예전 이미지 및 계정 선택 상황 확인. Android 홈 화면에서도 같은 흐름 확인.
