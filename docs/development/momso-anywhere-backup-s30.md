# momso anywhere 백업 S30 진행 기록

상태: **구현 중이며 아직 자동 백업이 켜지지 않는다.** 아래 부품을 설치 흐름에 연결하고 복구를 검증하기 전에는 VM 디스크의 자료가 다른 곳에 보존된다고 안내하지 않는다.

S46 준비: 서버의 실제 하위 경로에 있는 첨부 메타데이터 DB, 저장된 로그인과 AI 키 보관소, 코덱스 인증 파일을 암호화 사본에 포함한다. 상위 폴더가 심볼릭 링크면 거절하고 기존 파일은 덮지 않는다. **첨부 원본 파일 자체는 여전히 이 부품에 포함되지 않으며, 서버의 자동 종료 준비를 참으로 표시할 수 없다.** 이 데이터의 메모리 상한과 자동 실행·복구 연결도 남았다.

## 설계와 확인

- 고객 프로젝트의 비공개 버킷에 `momso-backup/slot-0.enc`부터 `slot-6.enc`까지 일곱 칸을 사용한다. SQLite 온라인 백업으로 쓰는 중인 DB의 일관된 사본을 만든다. 내용이 같으면 새로 올리지 않는다. 서로 다른 DB와 로그인 보관소 사이에 하나의 공통 시점은 보장하지 않는다.
- 각 사본마다 새 AES-256-GCM 데이터 키를 만들고, 고객 프로젝트의 Cloud KMS 키로 그 데이터 키를 암호화해 사본과 함께 둔다. VM을 지워도 프로젝트의 버킷과 KMS 키가 남으면 새 VM에서 복원할 수 있다. KMS 키를 영구 삭제하거나 고객 프로젝트에 접근할 수 없으면 이 백업은 풀 수 없다. 프로젝트 관리자와 VM의 전용 서비스 계정 권한을 신뢰한다. [Google Cloud KMS 봉투 암호화](https://docs.cloud.google.com/kms/docs/envelope-encryption), [SQLite 온라인 백업](https://www.sqlite.org/backup.html).
- VM 서비스 계정에는 해당 버킷의 객체 읽기·쓰기·덮어쓰기에 필요한 권한만, 해당 KMS 키에는 암호화·복호화 권한만 준다. 고정 이름을 덮어쓰려면 `storage.objects.create`와 `storage.objects.delete`가 모두 필요하다. [Cloud Storage 권한](https://docs.cloud.google.com/storage/docs/access-control/iam-permissions).
- 새 VM의 대상 파일이 없을 때 복원한다. 대상 파일이 이미 있으면 기존 것을 바꾸지 않고 복구 사본을 별도 이름으로 둔다. 이를 확인하고 고르는 화면은 아직 없다. 버킷과 KMS 키는 기본 삭제 대상이 아니다. 사용자가 명시적으로 고르면 소유권을 다시 확인한 버킷만 지우는 부품을 작성했으나 설치 흐름에는 아직 연결하지 않았다. KMS 키는 명시적 버킷 삭제 때도 보존한다.
- S21 로그인 보관소는 `vault.age`뿐 아니라 그것을 여는 age 개인 키가 필요하다. 호스트에 묶인 systemd 자격 증명을 다른 VM에서 그대로 읽을 수 있다고 가정하지 않는다. [systemd 자격 증명](https://www.freedesktop.org/software/systemd/man/latest/systemd-creds.html). 부품은 서비스에 전달된 개인 키를 백업 봉투 안에만 넣고, 새 VM에서는 `systemd-creds`로 그 호스트용 암호문을 만들도록 한다. 이 과정은 서버 시작 전의 설치 흐름에 아직 연결하거나 실제 Linux에서 검증하지 않았다. 키와 보관소가 서로 바뀌지 않는다는 점도 확인해야 한다.
- 한 번에 한 VM이 올리는 전제다. 두 VM이 동시에 같은 칸에 올릴 때의 조정은 아직 없다. 장기적으로 원자료를 위한 별도 공간이 필요하며 현재 몸소 폴더나 GitHub에는 손대지 않는다.
- 현재 서버의 Codex 연결은 별도 `CODEX_HOME`을 사용한다. 이 시제품은 그 폴더의 인증 자료를 포함하지 않으므로 새 VM에서 Codex 연결을 다시 해야 할 수 있다. 어떤 자격 증명을 안전하게 옮길지는 서버 연결 방식과 함께 확인해야 한다.
- 일곱 칸은 **현재 보이는 객체**의 수다. Cloud Storage의 기본 일시 삭제 보존이나 버전 관리가 켜져 있으면 덮어쓴 옛 객체가 추가로 남고 비용이 발생할 수 있다. [Cloud Storage 일시 삭제](https://docs.cloud.google.com/storage/docs/soft-delete).

## 아직 연결해야 할 일

1. 고객 프로젝트에 소유권을 확인할 수 있는 전용 비공개 버킷·KMS 키·최소 권한을 만들고, 기존 VM 및 휴대폰 설치 흐름 모두에 안전하게 연결한다. 준비 부품은 KMS 키 보관함만 만들어지고 키를 만들기 전에 중단된 경우 보관함의 소유권을 확인할 표식이 없어 자동 재개하지 못한다. 안전한 설치 기록과 재개 처리가 더 필요하다.
2. VM에 부품과 `python3-cryptography`를 설치하고, 매일 실행하는 timer와 유휴 종료 직전 실행을 연결한다. 갑작스러운 전원 손실 시 마지막 백업 이후 변경은 남지 않을 수 있다. 종료 스크립트만으로는 시간이 모자라 강제로 끊길 수 있으므로 유휴 종료를 결정하기 **전**에 백업 완료를 기다려야 한다. [Compute Engine 종료 스크립트](https://docs.cloud.google.com/compute/docs/shutdownscript).
3. 새 VM의 서버 시작 전에 복원하고 로그인 보관소의 age 개인 키를 새 VM에서 안전하게 제공한다. 기존 자료가 있으면 기존 것을 보존한다. 자격 증명을 만든 직후 중단된 경우 같은 키인지 대조하는 부품은 작성했지만 설치 흐름에서 실제 재개 시험은 하지 않았다. 기존 보관소의 복구 사본을 선택하는 절차도 필요하다.
4. 삭제 시 백업 보존을 기본값으로 하고, 명시적인 백업 삭제 선택을 소유권 검사와 함께 연결한다.
5. 암호화 부품은 현재 DB와 사본 전체를 메모리에 읽는다. 큰 데이터에서 스트리밍으로 바꾸고 메모리 사용량을 확인해야 한다. 온라인 SQLite 사본은 비공개 임시 디렉터리에 만들어지므로 실제 VM에서는 휘발성 `/run`을 사용하고 중단 시 정리 정책도 확인한다.

## 진행 기록

- 1단계: Google 로그인 앱 준비 순서를 기존 S26 문서 맨 위에 적었다.
- 2단계: 일곱 칸·암호화·SQLite 사본·충돌 보존용 독립 부품과 Google Storage/KMS 연결 부품을 작성했다. 제품 설치·실제 클라우드 연결 여부는 위 목록과 같다.
- 3단계: Windows에서 가짜 저장소·가짜 KMS 시험 11개가 통과했다. 첫 시험에서는 SQLite 연결을 닫지 않아 임시 폴더 정리에 실패했고, 연결을 닫도록 고친 뒤 다시 통과했다. Linux의 systemd·실제 Google API·설치 전체 흐름을 검증한 결과는 아니다.
