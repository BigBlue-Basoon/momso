# 입구 대용량 업로드와 스트림 (S170)

확인일 2026-11-25. [Google Cloud Run 요청 제한](https://docs.cloud.google.com/run/quotas#request_limits_for_cloud_run)에 따르면 HTTP/1 서버 요청은 32MiB, HTTP/2 서버 요청에는 그 한도가 없다. 클라이언트 연결이 HTTP/2라는 사실만으로 입구 컨테이너도 HTTP/2라고 가정하면 안 된다. HTTP/1 응답은 32MiB이나 chunked 또는 스트리밍은 이 한도가 적용되지 않는다. 공식 표는 HTTP/2 응답의 별도 숫자를 제시하지 않는다. 서비스 인스턴스당 동시 요청은 최대 1,000, HTTP/2 연결당 동시 스트림은 100이다. [요청 시간](https://docs.cloud.google.com/run/docs/configuring/request-timeout)은 기본 300초, 최대 3,600초다. 앱 입구는 HTTP/1이고 3,600초로 설정한다. 클라이언트나 중간 네트워크 제한은 별도다.

## 변경 전과 시험 범위

서버에는 이미 `/uploads`, `/uploads/{id}`, `/uploads/{id}/chunks?offset=`, `/uploads/{id}/finish` 이어 올리기가 있었다. 조각은 최대 8MiB, 오프셋 불일치와 미완성을 거절하고 전체 SHA-256은 제공된 경우에 확인한다. 원자료는 검증 뒤 보관한다. 과거 입구와 VM 프록시는 각각 요청 본문 전체를 메모리로 읽었고 입구는 32MiB 초과를 `400 invalid_request`로 거절했다. 512MiB 입구에서 동시 요청이 겹치면 본문만도 여러 개가 메모리에 존재할 수 있다.

화면 스냅샷 저장소 `master` `be899df`의 `apps/alpha/desktop/src/server-client.ts`를 읽어 확인한 결과, 실제 기존 `uploadAttachment`도 통째로 보내지 않고 4MiB씩 나눠 진행하며 재개한다. 다만 시작과 조각에서 전체·조각 지문을 보내지 않았다. 이를 보내는 수정과 단위 시험은 별도 스냅샷 가지 `codex/s170-mobile-upload`, 끝 `f591dc6187d2a9459266fcc23b0386ace4c26088`에 두었다. 이 가지는 기존 호출·화면 글·배치를 유지하며, 다른 화면 편집과 합쳐야 한다. 깨끗하게 의존성을 설치한 사본에서 화면 빌드와 기본 시험 3개가 통과했다. 스냅샷 `master`와 실제 배포본은 변경하지 않았다. 이 백엔드 가지의 `anywhere-upload.ts`는 별도의 재사용 함수다.

개발 VM의 격리된 Python 입구 프로세스와 가짜 로컬 뒤쪽에서 변경 전 10MiB 본문은 200, 프로세스 최대 RSS 33,288KiB였다. 40·200·1024MiB는 선언된 길이에서 400 `invalid_request`였고 본문은 보내기 전에 거절됐다. 따라서 그 크기의 실제 본문 전송량·메모리는 측정하지 못했다. 이 숫자는 입구와 가짜 뒤쪽이 같은 프로세스인 측정치이며 컨테이너 단독 메모리가 아니다. 이 VM에는 Docker 실행기가 없어 입구 이미지 자체와 실제 VM 프록시를 거친 시험이 아니다. Cloud Run 앞단도 재현하지 않는다.

## 조각 전송 변경

입구와 VM 프록시는 선언 길이만큼 작은 블록으로 전달한다. 서버의 기존 8MiB 이어 올리기 경로에 `X-Momso-Chunk-Sha256`을 추가하고, 64자리 소문자 SHA-256을 검증한다. 시작 시 전체 지문을 준 업로드에는 조각 지문도 필수이며 없으면 `invalid_chunk`, 다른 값이면 저장 전에 `integrity_error`를 반환한다. 기존 호출 호환을 위해 전체 지문을 보내지 않은 구형 업로드는 이 머리글 없이 계속 사용할 수 있다. 새 `uploadAnywhereFile` 함수는 각 조각의 지문과 시작 시 파일 전체 지문을 보낸다. 구형 경로까지 지문을 강제한 것은 아니다.

두 프록시의 블록 전달과 달리 서버는 조각 하나를 `Bytes`로 읽어 검증한다. 따라서 서버 메모리는 동시 조각 수에 따라 늘며, 최대 8MiB 조각 80개가 동시에 서버에 쌓이는 극단적 경우 본문만 최대 640MiB다. 새 화면 함수의 조각은 4MiB다. 이 수치는 단순 상한 계산이지 실측이나 전체 프로세스의 메모리 상한이 아니다. 다수 동시 파일의 실제 VM 부하는 확인하지 않았다.

전송이 끊긴 뒤 새 함수에 저장한 `uploadId`를 주면 파일의 전체 지문과 서버에 보관된 지문을 먼저 비교하고, 일치할 때 서버가 저장한 오프셋부터 이어 간다. 응답만 유실됐을 수 있으면 오프셋을 재조회한다. 만료된 미완료 조각은 마지막 수정 후 24시간이 지나면 정리 대상이며, 시작 시와 서버가 실행 중일 때 한 시간 간격으로 확인한다. 종료된 VM에서는 정리 작업이 실행되지 않으며 재시작 뒤 확인한다. 파일명과 media type의 유효성은 확인하나 형식별 허용 목록은 두지 않는다. 전송 길이는 서버 DB가 표현할 수 있는 signed 64비트 범위와 실제 디스크에 제한된다. 시작 시 같은 파일시스템이면 임시본과 원본에 필요한 크기의 두 배, 서로 다른 파일시스템이면 각 파일시스템의 여유를 확인한다. 확인 시점 뒤 공간이 달라질 수 있으므로 일부 파일·SQLite 쓰기의 실제 공간 부족도 `disk_low`로 분류한다. 모든 저장소 오류의 원인을 구별하는 보장은 아니다.

개발 VM에서 실제 서버의 저장소 부품에 10·40·200MiB와 1GiB 가짜 원자료를 8MiB씩 기록하고 전체 SHA-256을 비교하는 시험이 통과했다. 네 크기의 시험을 합쳐 약 74초였다. 이 시험은 Cloud Run·입구·VM 프록시·휴대폰을 거치는 종단 업로드가 아니다.

변경 뒤 개발 VM에서 입구 코드와 VM 프록시 코드를 차례로 통과해 가짜 뒤쪽으로 10·40·200MiB와 1GiB를 8MiB 조각으로 보냈다. 가짜 뒤쪽은 매 조각의 지문을 확인했다. 1GiB는 16.772초, Python 한 프로세스에 합친 입구·프록시·가짜 뒤쪽·송신기의 최대 RSS는 23,916KiB였다. 저장소까지 이어진 시험은 아니다. 별도로 이 PC의 Docker에서 실제 입구 이미지를 512MiB로 제한하고 같은 가짜 프록시·뒤쪽과 송신기를 실행한 시험도 네 크기를 통과했고 합산 최대 RSS는 23,072KiB였다. 이는 개발 VM의 이미지 시험이나 Cloud Run 요금·메모리 측정이 아니다.

추가로 이 PC에서 만든 입구 이미지의 파일시스템을 개발 VM으로 옮겨 양쪽 SHA-256을 대조한 뒤, 독립 폴더에서 이미지의 Python·입구 코드와 VM 프록시·가짜 뒤쪽을 `chroot`로 실행했다. 10·40·200MiB와 1GiB 조각 전송이 통과했고 1GiB는 8.257초, 한 프로세스 전체 최대 RSS는 25,212KiB였다. 동일 경로의 SSE는 1,800.1초 동안 181개 이벤트를 받고 정상 종료했다. 실제 VM의 Docker 컨테이너나 TLS, Cloud Run 앞단은 재현하지 않았다.

개발 VM에서 별도의 빈 시험 자료 폴더를 쓰는 실제 `momso-server`를 실행하고 입구·VM 프록시 코드를 통과시켜 4MiB 조각을 저장하는 종단 시험도 했다. 10·40·200MiB와 1GiB 모두 저장된 원본을 다시 읽어 전체 SHA-256이 일치했다. 각각 약 0.66·2.52·14.69·68.80초였다. HTTP는 로컬 가짜 개인 통로이며 이미지·TLS·실제 Google 앞단이나 휴대폰에서의 시험은 아니다. 임시 원자료는 시험 프로세스가 종료될 때 지운다.

## 본부의 실제 확인

- 순번 9 뒤 실제 소유자 세션으로 입구에서 40MiB·200MiB 파일을 올려 원본 크기와 SHA-256을 비교한다.
- 실제 휴대폰과 입구를 통해 30분 SSE를 확인한다. Google 앞단, 휴대폰 화면 잠금, 모바일 네트워크의 중단 여부는 로컬 시험으로 확인할 수 없다.
- 디스크 부족·중단 재개·동시 두 파일과 전송 후 백업을 별도로 확인한다. `disk_low`의 S167 통합본과 실제 전체 오류 경로를 대조한다.

가짜 응답·리눅스 로컬 결과와 실제 Google Cloud·휴대폰 결과는 별개다. 실제 Google·휴대폰 확인과 별도 스냅샷 가지의 통합은 아직 남아 있다.
