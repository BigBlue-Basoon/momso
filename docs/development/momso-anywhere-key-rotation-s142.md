# 운영 서명키 교체: 검증기 초안

## 현재 상태

PC 설치기·VM 작업자·시작 사이트와 브라우저에 root 확인을 연결했다. 가짜 키 시험은 실제 운영 키 생성이나 클라우드 배포를 대신하지 않는다. **실제 운영 키 생성·교체·운영 릴리스·휴대폰 확인은 아직 하지 않았다.**

## 공식 사례와 선택

TUF의 root 교체는 기존과 새 root 양쪽의 서명 정족수를 검증하고 버전을 한 단계씩 올려 저장한다. 만료된 메타데이터와 고정된 오래된 정보 문제도 다룬다. [TUF 명세](https://theupdateframework.github.io/specification/latest/). 전체 TUF의 timestamp·snapshot·targets 구현을 자체적으로 흉내 내어 완전한 TUF라고 부르지 않는다.

주 키와 예비 키 둘 중 **어느 하나의 서명만으로** 다른 키를 교체할 수 있다면, 한 키가 탈취된 공격자도 정상 키를 먼저 제거할 수 있다. 공격을 방지하면서 임의의 한 키 분실을 견디려면 여기서는 별도 키 세 개 중 두 서명을 root 교체에 요구한다. 예를 들면 온라인 릴리스 키 1개와 서로 독립된 곳에 보관하는 오프라인 복구 키 2개다. 두 복구 키만으로 탈취된 온라인 키를 제거할 수 있고, 한 키만 가진 공격자는 root를 바꿀 수 없다. 단, 릴리스 키가 털린 뒤 root 교체가 전파되기 전에는 공격자가 릴리스에 서명할 수 있다. 세 키 중 두 키가 함께 유출되거나 둘을 잃으면 이 방식도 보호·복구하지 못한다. 키 세 개와 교체 때 두 서명은 사용자의 원래 예시보다 추가 부담이다.

독립 검증기 `apps/alpha/desktop/src-tauri/momso-server-update/trust_rotation.py`는 3개의 Ed25519 SPKI 공개키, threshold 2, 릴리스 키 1개, 순번과 만료를 가진 원본 JSON을 검증한다. 교체본의 순번은 이전 값보다 정확히 1 커야 하며, 원본 바이트에 대한 유효한 서로 다른 서명이 이전 키 집합 2개와 새 키 집합 2개를 각각 충족해야 한다. S151부터 교체 root에는 서명된 `issuedAt`이 필수다. 이 시각이 직전 root 만료 전이고 발행 시각이 역행하거나 미래가 아니어야 한다. 현재 시각의 만료 검사는 맨 끝 root만 한다. `issuedAt`은 서명자의 주장이지 외부 타임스탬프 증명은 아니다. 중복 JSON 키, 중복 공개키, 만료된 최종 root, 이전·건너뛴 순번과 신뢰하지 않는 키의 서명은 거절한다. TUF 자체 포맷은 아니다.

## PC·VM 배포 계약

- 초기 신뢰 파일은 `scripts/momso_release_root.json`이다. `python scripts/momso_release_sign.py create-production-root --public-key <주 공개키> --public-key <예비1 공개키> --public-key <예비2 공개키> --expires <YYYY-MM-DDTHH:MM:SSZ> --output scripts/momso_release_root.json`은 순번 0과 threshold 2를 만든다. 이미 있는 파일을 덮어쓰지 않는다. 공개키만 사용하며 아직 운영 파일을 만들거나 게시하지 않았다.
- 교체 자산은 `trust-root-1.json`, `trust-root-1.sigs.json`처럼 숫자를 하나씩 올린다. JSON은 `version`, `issuedAt`, `expires`, `threshold`, `keys`, `releaseKey`를 갖고, 서명 파일은 해당 root 원본 바이트의 Ed25519 서명들을 `{SPKI_base64: signature_base64}` 객체로 담는다. 현재 root와 새 root 각각에서 다른 두 키의 서명을 확인한다. 공개 릴리스마다 첫 교체부터 현재까지 두 파일씩 모두 실어 PC가 같은 릴리스 경로에서 순서대로 찾을 수 있게 한다. 누락된 중간 순번이 있으면 뒤의 교체를 적용할 수 없다. 발행 명령은 [운영 안내서](momso-anywhere-production-s140.md)를 따른다.
- PC 설치기는 root 0에서 시작해 교체를 확인하고 설치 기록 옆 `.trust` 폴더에 마지막 상태를 보존한 다음 현재 주 키로 릴리스 서명을 검사한다. VM은 초기 root를 설정에 보관하고 `/var/lib/momso-update-trust/root.json`에 마지막 교체 상태를 원자적으로 기록한다. 작업자는 릴리스 검색 뒤 교체부터 적용하고 그 후 릴리스를 확인한다. 개발 채널은 기존 단일 키를 쓴다. 로컬 상태를 지우거나 이전 디스크 백업을 강제로 되돌리는 일까지 이 파일만으로 막지는 못한다.

## 연결 전 필수 사항

- 브라우저는 저장한 교체 이력을 초기 root부터 매번 서명 검증한다. 그러나 브라우저 저장소 초기화·새 기기에서 오래된 root가 제시되는 경우는 해결하지 못한다. 그 경우까지 rollback 방지를 주장해서는 안 된다.
- 최신 root를 숨기는 freeze 공격은 순번 검사만으로 막지 못한다. 신뢰할 수 있는 시각·만료와 루트 배포 접근성, root 만료 후 복구, 오프라인 고객의 교체 경로를 결정하고 검증해야 한다.
- 신뢰가 바뀐 뒤 기존 릴리스 키의 서명을 거절하고 개발 채널을 분리하는 가짜 시험을 수행한다. 운영 개인키를 AI가 생성·읽거나 저장하지 않는다. 실제 사용자·클라우드 시험은 별개다.
- 운영 생성 명령은 온라인 키 1개와 복구 키 2개를 만든다. 복구 키를 다른 곳에 옮기고 원래 복사본을 정리하는 일은 소유자가 한다. 종이 백업은 키 재입력과 오류 검출 방식이 검증되지 않았으므로 현재 지원한다고 주장하지 않는다.

## 데스크톱 Tauri

[Tauri updater 공식 문서](https://v2.tauri.app/plugin/updater/)는 설정의 `pubkey`와 builder에서 공개키를 지정하는 방법을 설명한다. 확인한 공식 설정과 builder는 단일 키이며 여러 키를 동시에 신뢰하는 내장 기능은 확인되지 않았다. 개인키를 잃으면 기존 설치에 새 서명 업데이트를 제공할 수 없다고 공식 문서가 경고한다. 기존 키로 서명한 업데이트를 통해 미리 교체 로직이나 새 키를 배포하는 길은 가능하지만, 이미 키를 잃거나 탈취당한 설치를 기존 자동 업데이트만으로 안전하게 되살리는 것은 별도 신뢰 경로나 재설치 없이는 보장할 수 없다. 구현은 이번 범위가 아니다.

질문: 오프라인 복구 키 두 개를 서로 다른 어디에 보관할지 개발자가 정해야 한다.
