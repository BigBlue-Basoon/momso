# server 올리기: 자료 복구 (S59)

PC 설치기의 기존 설치 갱신은 가능하면 작업 접수를 멈춘 뒤 `quiescent`를 확인한다. 작업이 끝나면 server를 중지하고 기존 server·화면·환경 설정과 `MOMSO_SERVER_DATA_DIR` 전체(DB, 암호화 보관소와 archive 포함)를 복사한다. 자동 업데이트 S38과 동일한 `DataSnapshots`를 사용하며, 파일과 폴더의 소유자를 유지한다. 자료 폴더 밖을 가리키는 심볼릭 링크는 대상이 복구 사본에서 빠지므로 올리기를 중단한다.

새 server나 화면 설치 또는 건강 확인에 실패하면 server를 멈추고 자료, server, 화면을 복원한 뒤 server를 다시 확인한다. 복구가 확인되지 않으면 사본과 작업 중지 상태를 보존한다. 복구된 이전 자료와 실패한 새 자료는 VM 안에 따로 남으며 평문으로 외부에 보내지 않는다. 대기 중인 사본이 있는데 새 올리기를 시작하면 덮어쓰지 않고 복구가 필요하다고 중단한다.

백업 연결 여부는 올리기를 막지 않는다. `/maintenance`가 없는 옛 서버는 `/activity`로 실행 중인 작업이 끝날 때까지 기다린 뒤 서비스를 멈춘다. `/activity`도 없는 판은 바로 서비스를 멈춘다. 옛 서버에는 신규 요청을 원자적으로 막는 수단이 없으므로 상태 확인과 서비스 중지 사이에 새 요청이 들어올 가능성이 있다. S56의 설치기 변경은 이 가지에 함께 반영했다.

시험 `scripts/test_momso_upgrade_systemd_s59.py`는 개발 VM의 별도 systemd 서비스와 가짜 상태 서버로 PC 설치기 갱신 경로를 호출한다. 가짜 새 판이 SQLite DB를 바꾼 뒤 건강 확인이 실패하면 DB·보관소·문서·화면이 이전 상태로 돌아오는지 본다. 실제 고객 VM과 고객 데이터는 사용하지 않는다.

당시 범위: S59 시점에는 PC 경로에서 입구 변경 실패가 자료 복구 분기에 연결되지 않았다. 현재 `upgrade_anywhere`는 server·화면과 관리 서비스 설치 뒤 입구 전환까지 같은 예외 처리로 감싸고, 실패 시 `upgrade_checkpoint('restore')`로 자료·실행 파일·화면·설정을 복원하고 건강을 확인한다. 자동 업데이트는 `update.py`의 `_rollback`에서 자료 사본, 이전 릴리스·순번·입구를 복원한다. 입구 자체의 이전 트래픽 복구는 별도로 확인한다. 이는 여러 단계를 복구하는 절차이지, 클라우드와 디스크 전체가 하나의 원자적 트랜잭션이라는 뜻은 아니다.

S129e 점검: 자료 사본에는 이전 SQLite 파일과 스키마가 함께 들어가므로 사본 복원이 성공하면 이전 server와 맞는 상태로 돌아간다. `test_upgrade_checkpoint_restores_server_and_screen_without_touching_other_files`는 SQLite 스키마 변경 뒤 이를 확인하고 관리 파일 복구 실패 시에도 자료와 실행 파일을 복구해 server 시작을 시도한다. 자동 업데이트의 `test_failure_restores_release_gateway_and_data`, `test_failed_gateway_rollback_does_not_leave_server_stopped`는 각각 복원과 입구 복구 실패를 가짜 호스트로 확인한다. 자료 복원 자체가 실패하면 `rollback_failed`와 사본을 보존한다. 복원 전 자료 폴더와 새 실행 파일이 그대로인 것이 확인되는 경우에는 그 새 판을 다시 켜고, 자료 폴더나 실행 파일의 짝이 확인되지 않으면 안전을 위해 다시 켜지 않는다. 자동 재기동이 실패하거나 하드웨어·디스크 오류가 있는 경우 server가 켜져 있다고 보장할 수 없다. 실제 고객 VM 시험은 하지 않았다.

자료 디렉터리를 통째로 복사하므로 그 안의 작업 파일과 캐시도 복구 사본에 포함된다. VM에 충분한 디스크 공간이 없으면 올리기를 중단하며, 나중에 실제 저장 구조별로 범위를 줄일 수 있다.
