시간은 한 번씩 잰 값이며 운영체제 캐시와 다른 작업의 영향을 받는다. 화면 표시, Tauri 직렬화, 네트워크 전송, 실제 회사 CLI와 Windows 전체 앱 시작은 포함하지 않는다. 한 채팅방 변경 저장과 복원에 각각 약 57초와 62초가 걸려, 이 규모에서는 더 빠른 설계와 실제 설치 앱 측정이 필요하다. 반복 저장 시험의 Git 이력은 첫 저장 한 개뿐이어서, 1년치 이력이 쌓인 뒤의 속도는 확인하지 못했다.

## 고친 것과 보존한 것

- 가져온 메시지의 지문이 없을 때 불필요하게 본문을 한 번 더 가리던 과정을 건너뛴다. 지문이 있으면 기존과 같이 원문 지문을 가린다.
- 가린 사본의 내용이 같으면 임시 파일을 만들고 기존 파일을 교체하지 않는다. 비밀값을 검사하고 생성한 결과와 바이트 단위로 비교한다.
- 첫 이력 유무를 문서마다 묻지 않고 검사 중 한 번 확인한다. 단순한 직선 이력이고 이름 변경이 없을 때는 최초 추가 시각을 묶어 읽는다. 병합·이름 변경이 있거나 묶어 읽지 못하면 각 파일의 기존 `git log --follow` 검사로 돌아간다. 이력은 검사 시작 시 확인한 HEAD를 기준으로 한다.
- 저장할 경로들을 명령줄 대신 NUL로 구분해 Git 표준 입력으로 전달한다. 선택한 파일만 저장하고 다른 준비된 변경은 보존한다. [Git 2.27 공식 문서](https://git-scm.com/docs/git-commit/2.27.0)는 이 옵션을 설명하며, 앱의 최소 지원 버전은 2.28이다.

## 저장소 크기와 GitHub

가짜 자료를 한 번 저장하고 압축한 `.git`은 804,401바이트였다. 한 채팅방에 짧은 말을 더해 저장하는 10번의 가짜 변경 뒤 `.git`은 압축 후 813,397바이트, 압축 전 981,161바이트였다. 같은 증가가 365번 이어진다고 단순 계산하면 각각 약 **1.13MB / 7.26MB**다. 실제로 365번을 측정한 값이 아니고, 서버의 크기와 개인의 실제 1년 사용량도 아니다. 사용자 자료가 덜 반복되거나 많은 방이 계속 바뀌면 훨씬 커질 수 있다. 원자료 바이트는 Git에 포함하지 않았다.

시험에서 가장 큰 채팅 사본은 약 0.98MiB였다. [GitHub 공식 안내](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)에 따르면 일반 Git 파일은 50MiB 초과 시 경고, 100MiB 초과 시 차단되며 저장소는 1GB 미만을 이상적으로, 5GB 미만을 강하게 권장한다. **이 가짜 시나리오**는 위 파일 크기와 권장 크기에 닿지 않는다. 실제 사용에서는 보장할 수 없다. Git은 변경 때 새 객체를 기록하며 압축·묶음 과정에서 유사한 내용의 차이를 이용할 수 있다. 이미 이력에 올라간 비밀값은 나중에 사본에서 가려도 옛 이력에 남는다.

## 다시 재기

이 시험은 기본 검사에서 제외된다. Windows PowerShell에서 저장소 루트의 기존 `target` 하나만 사용한다. 실행 전에 RAM 4GB 이상, C 드라이브 60GB 이상을 확인한다.

```powershell
$env:CARGO_PROFILE_DEV_DEBUG='0'
$env:CARGO_PROFILE_TEST_DEBUG='0'
$env:CARGO_INCREMENTAL='0'
$env:CARGO_BUILD_JOBS='1'
$env:CARGO_TARGET_DIR=Join-Path (Get-Location) 'target'
cargo test --manifest-path apps/alpha/desktop/src-tauri/Cargo.toml -j 1 synthetic_year_capacity -- --ignored --nocapture --test-threads=1
```

`MOMSO_SCALE_SMOKE=1`은 작은 자료로 시험만 하고, `MOMSO_SCALE_CHECK_ONLY=1`은 문서 1,000개 검사만 잰다. 두 값은 본 측정에서는 설정하지 않는다.
